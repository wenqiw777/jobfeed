# Real jobs and source postings

Status: implementation-ready after independent review and follow-up spot-check; no P0/P1 design blocker remains. This is design readiness, not runtime verification. No production code, database, runtime, or deployment change has been made by this plan.

## Result

One real requisition appears once in Triage, receives one current evaluation and one user workflow state, and is the unit of single and bulk actions. Every LinkedIn, Jobright, SpeedyApply, ATS, and other observed posting remains available as source evidence. A later scan of an already known requisition attaches a source to the existing real job instead of making a second Triage item.

This supersedes the current source-row-centered evaluation and display behavior **only after** the new identity and workflow paths are verified. Scan-time native-ID enrichment reuse and source-row retention remain in place.

## Data contract

1. Add `real_jobs(id, representative_job_id, created_at, updated_at, identity_review_state)` with an internal stable ID. `representative_job_id` is a nullable reference to the chosen source posting; it is not the identity of the real job.
2. Keep the existing `jobs` table as source postings. Add `jobs.real_job_id` as a foreign key. The `(platform, canonical_id)` uniqueness and every source URL, JD, date, and enrichment receipt remain source-specific. After backfill and verification, every source row has exactly one real job.
3. Add `real_job_identifiers(real_job_id, provider, scope, native_id, evidence_job_id, observed_url, observed_at)`. All three identifier parts are non-null; globally unique provider IDs use the fixed empty scope. Enforce unique `(provider, scope, native_id)`. `scope` identifies a vendor tenant/board when IDs are not global, such as the Workday host. One real job can have many identifiers. Store only observed vendor identifiers and links. A disputed identifier is withheld from active lookup and recorded with both source rows in a review case until ownership is resolved; never assign it to two real jobs or silently reassign it.
4. Add canonical workflow state/history and canonical current evaluation/claim records keyed by `real_job_id`. Preserve legacy source status/evaluation rows and history as audit during migration. The active read/write path must have one owner for each state; do not dual-write two independent statuses indefinitely.
5. Future application events refer to the real job and record the actual source posting and application URL; multiple submissions may belong to one real job. Historical `applied` rows identify a source job but did not store a submission URL: migrate that URL as unknown, never infer it from the source posting URL. Notes, follow-ups, interviews, decision history, and priority attach to the real job. Source-level JD corrections remain attached to the source posting and can invalidate the canonical evaluation when substantive input changes.
6. Add no hash fields, calculations, checks, or dependencies.

## Identity and merge contract

1. Native source IDs identify source rows, not necessarily real jobs. An observed ATS requisition ID or a shared LinkedIn/other vendor requisition ID is strong real-job evidence when employer and role facts do not conflict.
2. Capture the displayed Apply target and bounded redirect destination when available. Normalize only known tracking/query noise; preserve vendor-specific requisition IDs. Never infer an ATS ID from the employer homepage or from an unverified title. Browser capture must not submit an application.
3. Search same-employer/title candidates even when external IDs differ, using indexed lookup and an explicit candidate bound. Matching title, employer, location, or generic ATS host alone never merges. A candidate without a shared verified ID may auto-merge only after a source-content rule verifies the same substantive JD and no conflicting team, level, location-specific requirements, or requisition evidence. Ambiguous pairs remain separate and are reviewable. Do not run the current display-layer all-pairs JD comparison on the scan write path.
4. A source can join one real job only. An attempted join spanning two existing real jobs is atomic and reversible; reconcile identifiers, status, application and evaluation provenance before changing membership. Persist a review case with both real-job IDs, evidence and reason when the join is held. Never silently chain weak content matches into a larger group.
5. Once linked, later scans resolve through the identifier table first, then the bounded candidate comparison. A confirmed repost of the same requisition stays in its real job; a new requisition number starts a separate real job unless independently proven equivalent.
6. Southwest LinkedIn `476978` and the Southwest ATS/Jobright records, and Qualcomm LinkedIn `476964` and Jobright `475374`, are positive acceptance cases **only after** their ATS destination or substantive JD equivalence is verified. Tebra `444342` is a known old source row: grouping its aliases does not imply that viewing it should remove it from Results.

## Evaluation and workflow contract

1. Build one deterministic canonical input per real job. Prefer an authoritative, complete ATS JD, otherwise the highest-quality complete source JD; take title, level, pay, eligibility, and source-dependent scoring facts from that representative. Use the verified location set only when requirements are shared across locations; otherwise split the requisitions or hold for review. Use the earliest trustworthy original posting date, the first source discovery date, and official ATS closure evidence for canonical freshness/closed state. Preserve repost observations per source; one alias's repost flag does not by itself turn the whole real job into a new posting. Record the selected source and every field used by filtering, ML, Stage A/B, sorting, and priority. If sources contain materially different requirements, hold the group for review or split it before scoring.
2. Convert latest-scan/today source-job ID scopes to distinct `real_job_id` values before claims and show separate counts for newly found sources versus unevaluated real jobs. Claim, gate, and evaluate by `real_job_id`, so concurrent source scans cannot score the same real job twice. A new alias does not rescore a completed real job. A substantive canonical input or model-policy change marks the current evaluation stale and queues reevaluation; the old score stays in history but is not displayed as current. A repost-only observation does not queue a second paid evaluation. Existing repost skip policy applies to a new real job only after canonical evidence is selected.
3. One real-job status drives Results, Wait, Applied, and Ignored. Single-row and bulk transitions operate on distinct `real_job_id` values in one transaction per real job. A source alias never receives an independent user decision after cutover.
4. Existing conflicting source decisions are not settled by timestamp. Preserve every historical decision and application record. During backfill, identical statuses merge; `new`/`scored` are neutral and yield to an existing explicit decision. Any two different explicit statuses (`shortlisted`, `awaiting_referral`, `applied`, `interviewing`, `offer`, `rejected`, `ghosted`, `archived`, `ignored`) hold the proposed merge for review, with original rows and statuses intact. This includes the known Applied/Ignored case: its Applied decision stays recorded, but the two source rows are not silently made one canonical status. `Applied` status alone is not proof that a submission occurred. A later source-level status can never downgrade an Offer or erase an Applied decision. If identity evidence or role facts conflict, hold the merge for review as well.
5. Auto-decay, attention/reminders, digests, application statistics, priority snapshots, and other workflow consumers read canonical status after cutover, so one real job cannot create duplicate reminders or counts. Library can expose all source postings, but each shows its parent real job and canonical decision. Triage shows one row per real job and its detail shows every source and the evidence used to link them. First-seen date and repost evidence remain distinct.

## Interfaces and compatibility

- Use a distinct `/api/real-jobs/{real_job_id}` namespace for Triage list/detail, transitions, notes, follow-ups, interviews, and bulk actions. Never interpret a bare old `/api/jobs/{source_job_id}` number as a real-job ID: independently generated integer IDs can overlap. Preserve `/api/jobs/{source_job_id}` as the source-posting detail/JD route; legacy source-status actions explicitly resolve its `real_job_id` and return that canonical identity during client migration. Return the representative source for the Triage card/JD plus a source list and canonical status/evaluation. An old saved source-job link must still open that source posting.
- Library search remains able to find every source posting and open its original URL/JD. Results counts, pagination, select-all, bulk counts, sorting, and priority snapshots count real jobs, not aliases. Raw source/scan diagnostics continue to count source rows and label them accordingly.
- SQLite and PostgreSQL must implement the same identity, backfill, claim, status, and view contracts. Migration and rollback evidence must cover both backends before activation.

## Acceptance and risks

- Verified aliases of one requisition produce one Triage item, one current evaluation, and one canonical decision. Applied or Ignored aliases do not reappear in Results. Different requisitions with the same employer/title remain separate.
- Existing source rows, URLs, JDs, first-discovery dates, evaluation history, status history, and available application evidence are not deleted or overwritten by grouping. Historical submission URLs remain unknown when not previously captured.
- The known exact-identifier Applied/Ignored conflict is reported and held as two real jobs until review, retaining its original Applied decision; the 14 same-company/title Applied/Ignored groups are only candidates, not automatic merges. A mixed Applied/Offer or other explicit-status pair is likewise held rather than downgraded.
- Main risks are false merges, missed merges when Apply destinations are unavailable, evaluation-input changes across sources, conflict migration, query latency over the current large corpus, and divergence between SQLite/PostgreSQL. The tasks above each carry an explicit positive and negative verification for those risks.

## Review disposition

An independent read-only review found ID-route collision, online-write/backfill gaps, missing historical application URLs, source-ID evaluation scope, incomplete canonical scoring inputs, vendor ID scope, background status consumers, and unbounded content-comparison cost. The revised contracts and tasks above address each. Follow-up review found no remaining P0/P1 design contradiction after adding non-null identifier scope, a full explicit-status conflict rule, and evidence-gated concurrent collision handling. Runtime behavior remains unverified until the corresponding implementation tasks pass.
